# ADR 0002: Layout budgets and whether layout runs in a Web Worker

- **Status:** Accepted (2026-10-21)
- **Epic:** roadmap M4.0 ⚑ (layout spike)
- **Relates to:** [layout §16](../spec/layout.md#16-performance-budgets-and-benchmarks), [architecture §5.3, §11, §15.3](../architecture.md#11-performance-budgets), NFR-PERF-01, NFR-PERF-04

## Context

Layout §16.1 set provisional budgets: full layout of a 7-box, 40-arrow diagram in at most 5 ms native and 15 ms wasm32 (p95), and Auto-Arrange in at most 300 ms native and 1 s wasm32. It left open whether layout must move to a Web Worker to protect the 16 ms keystroke budget (NFR-PERF-01). The spike prototyped the expensive parts and measured them before M4.3 commits to the routing design.

**What the spike built** (`idef0_layout::spike`, to be replaced by M4.1–M4.3 and M4.7):
- box sizing (§4.1–4.2, Mono metrics) and port positions (§4.4);
- staircase placement, iteration 1 (§5.1);
- global routing: the §6.2 templates, the §6.3 cost with keep-out and short-segment rejection, and the §6.4 order with up to 3 rip-up passes;
- Auto-Arrange Step 1, the §12.2 box-order branch and bound with its lower bound.

**What it did not build:** track assignment (§7), labels (§11), fillets, bundles and bridges (§8–§10), the Scene and SVG (§14), and Auto-Arrange Steps 2–3. It routes on channel center lines, so its crossing counts are pessimistic. Each bundle branch or leaf is routed as its own edge.

**Fixtures** (layout §16.4), generated by `scripts/gen-bench-fixtures.py`:
- `fixtures/bench/dense-7x40.idef0`: 7 boxes, 40 arrows, every §6.2 template class;
- `fixtures/bench/arrange-worst-7.idef0`: 7 boxes, all 42 ordered pairs as control arcs in a scrambled order, plus a 9-arrow input side (52 arrows);
- the dogfood model.

**Method.** `scripts/layout-spike/measure.sh`, run by `.github/workflows/layout-spike.yml` on the reference machine (architecture §15.3), produces:
- native wall-clock: 300 iterations after a warm-up;
- callgrind instruction counts: one run per operation, minus a baseline run that only parses the fixtures;
- wasm32 wall-clock: the same harness built for `wasm32-wasip1` and run under Node's WASI. Node uses V8, the engine Chromium uses. Headless Chromium through `wasm-bindgen-test` arrives with the CI browser epic.

## Measurements

Reference machine: GitHub-hosted `ubuntu-24.04`, AMD EPYC 7763, Linux 6.17 x86_64, Rust 1.96.0; Node 22.23 for wasm32. Run [39618597706](https://github.com/ArthurKeen/idef0-rs/actions/runs/39618597706).

| Operation | Native median / p95 | wasm32 median / p95 | Instructions |
|---|---|---|---|
| Placement, `dense-7x40` | 8 / 13 µs | 35 / 51 µs | 94 k |
| Placement + global routing, `dense-7x40` | 191 / 208 µs | 276 / 545 µs | 2.65 M |
| Placement + global routing, worst case (52 arrows) | 221 / 231 µs | 323 / 347 µs | 2.99 M |
| Placement + global routing, dogfood A0 | 37 / 39 µs | 54 / 65 µs | 0.47 M |
| Auto-Arrange Step 1, worst case | 1.09 / 1.11 ms | 1.37 / 1.44 ms | 15.2 M |
| Parse `dense-7x40` (for scale) | 163 / 191 µs | 392 / 611 µs | 1.58 M |

A developer laptop (Apple M-series, macOS, Node 26) gave the same picture: global routing of `dense-7x40` took 99 / 119 µs natively and 103 / 119 µs in wasm32, and Step 1 took 0.50 ms and 0.61 ms.

**Workload facts** were identical natively and in wasm32, on both machines, which is a cross-target determinism check of the prototype:
- `dense-7x40`: all 40 edges routed in 2 passes; 178 template candidates evaluated in total; 74 bends; 104 crossings (pessimistic, because routes run on channel center lines);
- worst case, Step 1: proxy cost 22,174 → 22,120, best order `[3, 0, 1, 2, 4, 5, 6]`; branch and bound visited 8,663 nodes and reached only 3 of the 5,040 leaves.

**Findings.**
1. The template parameter space is far smaller than §16.2 assumed: about 2 candidates per edge per pass, not 49. Global routing costs about 0.2 ms native and 0.55 ms wasm32 p95 for the 7×40 fixture, 25–30× below the full-layout budget.
2. The §12.2 lower bound prunes almost everything: 3 leaves instead of 5,040. Step 1 is about 1.5 ms in wasm32, roughly 700× below the 1 s Auto-Arrange budget.
3. wasm32 under V8 ran 1.0–2.6× slower than native at p95, in line with the "1.5–3×" estimate of §16.2.
4. The crossing count on channel center lines is high (104 for 40 edges). Track assignment (§7, M4.4) is needed for real crossing numbers. It is not a performance concern (O(m²) per channel, m ≤ 40).

## Decision

1. **Layout runs on the main thread in v1.** No Web Worker for layout. The measured global routing, the dominant cost by §16.2, uses about 4 % of the 15 ms wasm32 budget. Track assignment, labels, fillets, bridges and the SVG render are estimated below routing (§16.2), so even a 10× margin over the measured routing stays under 6 ms p95 in wasm32.
2. **The §16.1 budgets stand unchanged** (5 ms native and 15 ms wasm32 for full layout, 300 ms and 1 s for Auto-Arrange). The spike does not relax them. It does not tighten them either, because the measured stages are a subset of the full layout.
3. **Re-check gate at M4.5.** When the real `layout → Scene → SVG` exists, the `layout-spike` workflow (or its M5.7 successor) measures full layout plus SVG render on `dense-7x40`. If wasm32 p95 exceeds 15 ms on the reference machine, this decision flips: layout moves to the Web Worker and the UI shows the previous Scene until the new one arrives (§16.1). That flip needs a superseding ADR. *Re-checked at M4.5:* the `render` operation (full layout, Scene and SVG on `dense-7x40`) measured 1.57 ms p95 native and 1.74 ms p95 on wasm32 under Node on the development machine, against the 15 ms threshold, so the decision stands. The `layout-spike` workflow records the reference-machine numbers.
4. **Auto-Arrange stays in the Web Worker**, as layout §12.6 and architecture §5.3 already require. Step 1 alone would fit on the main thread. Steps 2–3 and the guard add three full layouts plus port permutations, and keeping the whole run off the keystroke path costs little. The 200 ms progress-indicator threshold stays.
5. **The validation Worker question is not decided here.** It depends on the M3.1 Mangle measurement (architecture §5.3, ADR 0001). This ADR's result leaves validation the remaining ~15 ms of the keystroke budget after layout.
6. **Instruction counts are reference points, not yet gates.** The gated `bench-gate` baselines (gungraun, testing §6) are set in M5.7 against the real engine. Until then the `layout-spike` workflow is informative and runs on changes to layout, the harness or the bench fixtures.

## Consequences

- M4.1–M4.3 implement sizing, placement and global routing as specified. No Worker plumbing is needed for layout in M7.x.
- M4.4 (track assignment) must report crossing counts. The spike's 104 crossings on center lines are not a baseline for `crossings.json`. *Done in M4.4:* `layout-spike` reports the exact crossings after track assignment, and `fixtures/layout/baselines/crossings.json` records them.
- The spike module, `scripts/layout-spike/` and the workflow stay until M4.3 replaces the prototype. M4.3 either ports the harness to the real API or removes it along with the module. *Done in M4.3:* the harness now times the real sizing, placement iteration and global routing (`layout_routes`), and the module keeps only Auto-Arrange step 1 until M4.7.
- Risk: Chromium's wasm tier-up or GC could differ from Node's V8. The browser CI epic re-measures with `wasm-bindgen-test`. The headroom (25×) makes a flip unlikely.
